# Java Programming Project – Assessment Rubric

## 1. Assessment Overview

Total: **100 points**

| Criteria                              |   Weight |
| ------------------------------------- | -------: |
| Problem, Requirements & Project Scope |      10% |
| Java/OOP Design & SOLID               |      20% |
| Technical Implementation              |      25% |
| Testing, Debugging & Evaluation       |      15% |
| Novelty & Technical Contribution      |      15% |
| Code Quality & Documentation          |      10% |
| Presentation & Viva                   |       5% |
| **Total**                             | **100%** |

---

# 2. Problem, Requirements & Project Scope – 10%

Evaluate:

* Clarity of the problem.
* Clearly defined objectives.
* Functional requirements.
* Non-functional requirements.
* Appropriate project scope.
* Appropriate system architecture.

A strong project should clearly explain **what problem it solves and why the selected architecture is appropriate**.

---

# 3. Java/OOP Design & SOLID – 20%

Evaluate:

* Encapsulation.
* Abstraction.
* Inheritance.
* Polymorphism.
* Interfaces.
* Composition.
* Class responsibilities.
* Dependency management.
* SOLID principles.
* Design patterns where appropriate.

The project should demonstrate meaningful use of OOP rather than simply placing all functionality into a small number of large classes.

---

# 4. Technical Implementation – 25%

Evaluate the technical implementation relevant to the selected project.

Possible areas include:

### I/O

* Text I/O.
* Binary I/O.
* Object I/O.
* Serialization.
* NIO.

### Concurrency

* Threads.
* Synchronization.
* Thread Pool.
* Concurrent processing.

### GUI

* Swing/JavaFX.
* Event handling.
* State management.
* Animation.
* Drawing.

### Networking

* Socket.
* TCP/UDP.
* Client/Server.
* Multiple clients.
* Protocol/message design.

### Database

* SQL.
* JDBC.
* CRUD.
* PreparedStatement.
* Transactions.

### Functional Programming

* Lambda.
* Streams.
* Functional interfaces.
* Data processing.

### Meta-Programming

* Reflection.
* Annotations.
* Dynamic Proxy.
* Bytecode/AOP.

**Students are not required to use all of these technologies.**

Evaluation should focus on whether the selected technologies are:

* Appropriate for the problem.
* Correctly implemented.
* Properly integrated.
* Clearly understood by the students.

---

# 5. Testing, Debugging & Evaluation – 15%

Evaluate:

* Test cases.
* Unit testing.
* Integration testing.
* System testing.
* Debugging.
* Error handling.
* Experimental design.
* Metrics.
* Results.

Projects involving concurrency, networking, databases, or performance should include testing scenarios relevant to those characteristics.

---

# 6. Novelty & Technical Contribution – 15%

Evaluate what the group has **designed, developed, or improved**.

Possible contributions include:

* Algorithm.
* Architecture.
* Data processing.
* Concurrency mechanism.
* Network protocol.
* Performance optimization.
* Database optimization.
* GUI/state architecture.
* Design pattern.
* Custom framework/component.
* Reflection/annotation mechanism.
* Testing mechanism.
* Fault/error handling.
* Improvement over an existing project or baseline.

Purely visual changes such as colors, fonts, icons, or layout changes are not considered a major technical contribution.

---

# 7. Code Quality & Documentation – 10%

Evaluate:

* Coding conventions.
* Naming.
* Code organization.
* Comments/documentation.
* Exception handling.
* Code duplication.
* Maintainability.
* Git collaboration.
* README quality.
* Installation/run instructions.

The submitted source code should be sufficiently complete for the instructor to build and run the project.

---

# 8. Presentation & Viva – 5%

The group should present:

1. Problem.
2. Architecture.
3. Main functionality.
4. Technical implementation.
5. Novelty/Contribution.
6. Testing and results.
7. Limitations.

Each member should understand the part of the project they contributed to.

During the viva, the instructor may ask a student to:

* Explain a class.
* Explain a method.
* Run a feature.
* Debug an error.
* Modify a piece of code.
* Explain why a particular technology was selected.

---

# 9. Important Conditions

The project may be seriously affected during assessment if:

* The source code cannot be built or run.
* The submitted source code is not the group's own work.
* The report does not accurately describe the source code.
* Unauthorized source code has been copied.
* Experimental results are fabricated.
* A student cannot explain the code they claim to have developed.
* The submission is incomplete.

---

# 10. Compilatio

The final report must be checked using Compilatio.

Required similarity threshold:

**Similarity ≤ 20%**

Students must:

* Properly cite sources.
* Avoid copying without attribution.
* Identify reused materials where appropriate.

The similarity report is a supporting tool for checking the report; the final assessment should consider the context, citations, source material, and submitted work.
